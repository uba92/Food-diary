## 2. Fix backend (correttezza API)

### 2.1 — La POST dei pasti restituiva nome/quantità vuoti

`PlannedMealService.CreatePlannedMealAsync` salvava il pasto ma non caricava la navigation
`FoodAlternative`, così il DTO di risposta aveva i campi del cibo vuoti. Il fix sfrutta
l'entità già recuperata per la validazione:

```csharp
var meal = await _plannedMealRepository.AddPlannedMealAsync(PlannedMealMapper.ToEntity(request));
meal.FoodAlternative = foodAlternative; // navigation già disponibile → niente nome/quantità vuoti
await _plannedMealRepository.SaveChangesAsync();
return PlannedMealMapper.ToResponseDto(meal);
```

Nessuna query extra: `foodAlternative` era già stato letto per controllare l'esistenza.

### 2.2 — Le PUT restituivano `true` invece dell'oggetto aggiornato

`UpdateWeeklyPlanAsync` e `UpdatePlannedMealAsync` ritornavano `bool`, quindi le PUT
rispondevano `true`. Sono state portate a ritornare il **DTO aggiornato** (o `null` se non
trovato), coerentemente con `FoodAlternative`:

```csharp
// firma del servizio: da Task<bool> a Task<WeeklyPlanResponseDto?>
public async Task<WeeklyPlanResponseDto?> UpdateWeeklyPlanAsync(int id, UpdateWeeklyPlanRequest request)
{
    var entity = await _weeklyPlanRepository.GetWeeklyPlanByIdAsync(id);
    if (entity == null) return null;            // → 404 nel controller
    if (request.StartDate >= request.EndDate)
        throw new ArgumentException("Start date cannot be later than end date.");
    entity.StartDate = DateTime.SpecifyKind(request.StartDate, DateTimeKind.Utc);
    entity.EndDate = DateTime.SpecifyKind(request.EndDate, DateTimeKind.Utc);
    await _weeklyPlanRepository.SaveChangesAsync();
    return WeeklyPlanMapper.ToResponseDto(entity); // → 200 con il DTO
}
```

### 2.3 — ID non validi → 400 JSON coerente

In `PlannedMealService` un `WeeklyPlanId`/`FoodAlternativeId` inesistente ora lancia
`ArgumentException`, intercettata dal `GlobalExceptionHandler` che la traduce in
`400 { "error": ... }`. Nella PUT si distingue inoltre il pasto non trovato (404) dagli id
non validi (400):

```csharp
if (weeklyPlan == null || foodAlternative == null)
    throw new ArgumentException("Invalid WeeklyPlanId or FoodAlternativeId."); // → 400
```

## 4. Vista per giorno e assegnazione pasti

È il cuore mancante dell'app. Nuova `WeeklyPlanDetailPage` (rotta `/weekly-plans/:id`):

- usa `GET /api/weeklyplan/{id}/by-day` per ottenere i 7 giorni (`monday`..`sunday`);
- per ogni giorno mostra i pasti e un `select` + `+` per assegnarne di nuovi;
- mostra il **pannello frequenze** da `GET /api/weeklyplan/{id}/usage-stats` con avviso per
  gli alimenti oltre il limite (`IsOverLimited`);
- dopo ogni aggiunta/rimozione ricarica i dati.

Nota tecnica importante: il backend **non** ha un `JsonStringEnumConverter`, quindi
`DayOfWeekType` viaggia come **intero** (Monday=0 … Sunday=6). Il frontend invia `dayOfWeek`
come numero:

```jsx
await createPlannedMeal({ dayOfWeek: day.value, weeklyPlanId: planId, foodAlternativeId });
```

Le card dei piani in `WeeklyPlansPage` sono diventate `Link` cliccabili verso il dettaglio.

## 6. Categoria alimentare + raggruppamento a tab

### 6.1 — Backend: nuovo campo `FoodCategory`

Aggiunto `FoodCategory` (stringa **nullable**, coerente con `MealType`) a model, DTO
(create/update/response), mapper e service di update. Migration `AddFoodCategoryToFoodAlternative`:

```sql
ALTER TABLE "FoodAlternatives" ADD "FoodCategory" text;
```

Nullable per non rompere le righe esistenti (mostrate poi come "Senza categoria").

### 6.2 — Frontend: select categoria + tab di raggruppamento

Nel form un nuovo select **Categoria** (Proteine, Cereali, Verdura, Frutta, Latticini,
Grassi, Altro). Sopra l'elenco due **tab**: *Per tipo di pasto* | *Per categoria*. La lista
non è più piatta ma divisa in sezioni con intestazione e contatore. Funzione di
raggruppamento che rispetta l'ordine predefinito e mette il bucket "non assegnato" in fondo:

```jsx
function groupFoods(foods, key, order, fallbackLabel) {
  const groups = {};
  for (const food of foods) {
    const label = food[key]?.trim() || fallbackLabel;
    (groups[label] ??= []).push(food);
  }
  const ordered = order.filter((o) => groups[o]);
  const extras = Object.keys(groups)
    .filter((l) => !order.includes(l) && l !== fallbackLabel).sort();
  const tail = groups[fallbackLabel] ? [fallbackLabel] : [];
  return [...ordered, ...extras, ...tail].map((label) => ({ label, items: groups[label] }));
}
```

## 8. Feature diario sintomi + PDF

Obiettivo: registrare i sintomi giorno per giorno, correlarli agli alimenti **realmente
mangiati**, ed esportare un **PDF** per la nutrizionista. Decisioni di design concordate:
flag "mangiato" sui pasti; data **+ ora** del sintomo; tipi sintomo da **lista + "Altro"**;
PDF generato dal **backend con QuestPDF**.

### 8.1 — Passo 1: flag "mangiato" sui pasti

`PlannedMeal.Eaten` (bool) aggiunto a model, `UpdatePlannedMealRequest`, response DTO,
entrambi i mapper e a `UpdatePlannedMealAsync`. Migration:

```sql
ALTER TABLE "PlannedMeals" ADD "Eaten" boolean NOT NULL DEFAULT FALSE;
```

Nel frontend ogni pasto ha una checkbox "mangiato" che usa la PUT esistente:

```jsx
await updatePlannedMeal(meal.id, {
  dayOfWeek: meal.dayOfWeek, weeklyPlanId: planId,
  foodAlternativeId: meal.foodAlternativeId, eaten: !meal.eaten,
});
```

I pasti consumati sono evidenziati (sfondo verde + ✓). Questo flag è il prerequisito per
correlare i sintomi solo a ciò che è stato davvero mangiato.

### 8.2 — Passo 2: CRUD backend `SymptomEntry`

Slice verticale completo (model, DTO, mapper, repository, service, controller) seguendo il
pattern del progetto. Modello:

```csharp
public class SymptomEntry
{
    public int Id { get; set; }
    public DateTime OccurredAt { get; set; }   // data + ora, UTC
    public string Type { get; set; } = string.Empty;
    public int Severity { get; set; }          // 1..5
    public string? MealType { get; set; }      // momento (Colazione/Pranzo/…)
    public string? Notes { get; set; }
    public int? FoodAlternativeId { get; set; }// alimento sospetto (opzionale)
    public FoodAlternative? FoodAlternative { get; set; }
}
```

La data segue la convenzione UTC del progetto (mapper):

```csharp
OccurredAt = DateTime.SpecifyKind(request.OccurredAt, DateTimeKind.Utc),
```

Validazione nel service: `Type` obbligatorio, `Severity` 1–5, `OccurredAt` valorizzata,
`FoodAlternativeId` esistente se presente. Endpoint:

- `GET /api/symptomentry?from=&to=` (intervallo o tutti)
- `GET/POST/PUT/DELETE /api/symptomentry`

Migration `AddSymptomEntry`: crea la tabella `SymptomEntries` con FK opzionale verso
`FoodAlternatives`.

### 8.3 — Passo 3: UI inserimento sintomi (per giorno)

`components/SymptomFormModal.jsx`: modale con Tipo (lista predefinita + "Altro" a testo
libero), Severità 1–5, Ora, Momento, Alimento sospetto, Note. Stato inizializzato dalle
props e **`key` dal parent per il remount** (niente `useEffect` di sincronizzazione, lint
pulito):

```jsx
{symptomModal.open && (
  <SymptomFormModal
    key={`${symptomModal.dateIso}-${symptomModal.initial?.id ?? "new"}`}
    dateIso={symptomModal.dateIso} foods={foods}
    initial={symptomModal.initial}
    onSave={handleSaveSymptom} onCancel={closeSymptomModal} />
)}
```

In `WeeklyPlanDetailPage` ogni giorno carica i propri sintomi e li mostra con un pallino
colorato per severità. La data del giorno si calcola dall'inizio del piano:

```jsx
function dayDate(startIso, offset) {
  const d = new Date(startIso);
  d.setUTCDate(d.getUTCDate() + offset); // offset = indice del giorno (Lun=0)
  return d.toISOString().slice(0, 10);   // YYYY-MM-DD
}
```

L'ora viene combinata con la data nel formato `YYYY-MM-DDTHH:mm:00` (stringa
`${dateIso}T${time}:00`).

### 8.4 — Passo 4: aggregazione report

`ReportService.GetReportAsync(from, to)` produce un `SymptomReportDto` con:

- **timeline giornaliera** (alimenti mangiati + sintomi del giorno);
- **frequenza sintomi** (conteggio + severità media per tipo);
- **correlazioni alimento↔sintomo** = co-occorrenza per giorno (NON causalità).

La data del pasto consumato si ricava da `WeeklyPlan.StartDate + DayOfWeek`, e si considerano
**solo i pasti con `Eaten == true`**:

```csharp
foreach (var meal in plan.PlannedMeals)
{
    if (!meal.Eaten || meal.FoodAlternative == null) continue;
    var date = plan.StartDate.Date.AddDays((int)meal.DayOfWeek);
    if (date < fromUtc.Date || date > toUtc.Date) continue;
    // ... raggruppa per data
}
```

La correlazione conta, per ogni alimento, i giorni in cui è stato mangiato e quanti di quei
giorni hanno avuto un sintomo:

```csharp
var symptomDays = datesEaten.Where(d => symptomsByDate.ContainsKey(d)).ToList();
// DaysEaten = datesEaten.Count, DaysWithSymptom = symptomDays.Count
```

Endpoint `GET /api/report?from=&to=`. Frontend `ReportPage` (rotta `/report`, voce navbar
"Report"): selettore intervallo, tabelle Correlazioni e Frequenza, Diario giornaliero, e un
**disclaimer** che chiarisce che si tratta di co-occorrenza e non di causa-effetto.

> Dettaglio React: il caricamento iniziale usa una funzione async **inline** dentro
> `useEffect` (lo stato viene aggiornato solo dopo `await`) per rispettare la regola eslint
> `react-hooks/set-state-in-effect`.

### 8.5 — Passo 5: export PDF con QuestPDF

Aggiunto il pacchetto **QuestPDF 2026.6.0** e impostata la **licenza Community** in
`Program.cs`:

```csharp
QuestPDF.Settings.License = QuestPDF.Infrastructure.LicenseType.Community;
```

`Helpers/SymptomReportDocument.cs` implementa `IDocument` e compone il PDF (intestazione,
disclaimer, tabelle Correlazioni e Frequenza, Diario giornaliero, footer con pagina).
Endpoint che restituisce il file:

```csharp
[HttpGet("pdf")]
public async Task<IActionResult> GetReportPdf([FromQuery] DateTime from, [FromQuery] DateTime to)
{
    var report = await _reportService.GetReportAsync(from, to);
    var bytes = new SymptomReportDocument(report).GeneratePdf();
    var fileName = $"report-sintomi-{report.From:yyyyMMdd}-{report.To:yyyyMMdd}.pdf";
    return File(bytes, "application/pdf", fileName);
}
```

Nel frontend il bottone **Esporta PDF** scarica il blob:

```jsx
const blob = await downloadReportPdf(`${range.from}T00:00:00`, `${range.to}T23:59:59`);
const url = URL.createObjectURL(blob);
const link = document.createElement("a");
link.href = url; link.download = `report-sintomi-${range.from}_${range.to}.pdf`;
link.click(); URL.revokeObjectURL(url);
```

Il service axios usa `responseType: "blob"` per ricevere i byte del PDF.

## 10. Punti aperti

- **FK alimento↔sintomo**: la FK è `ON DELETE NO ACTION`. Eliminare un `FoodAlternative`
  referenziato da un `SymptomEntry` fallisce a livello DB e oggi l'errore non è gestito dal
  `GlobalExceptionHandler` → 500. Da risolvere con `ON DELETE SET NULL` (nuova migration) o
  gestendo l'eccezione.
- **Nessun test automatico**: la logica di correlazione del `ReportService` è il primo
  candidato sensato.
- Eventuale **pagina "Diario sintomi"** indipendente dai piani (oggi i sintomi si inseriscono
  dal dettaglio di un piano).
- **Fuso orario**: l'ora dei sintomi è salvata as-is in UTC (adeguato per un'app mono-utente).
